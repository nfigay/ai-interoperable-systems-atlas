# E3.1 — Compound Graphs and Federated Configurations

## Status and scope

Experimental, non-normative **Atlas** profile. `*-demo` realizations and configurations are fictitious; they serve to test the model and provide **no evidence of operational interoperability**. E3.1 introduces a composite registry independent of the drawing engine, a Cytoscape projection, and a validator. It is not a SAT/SMT solver, STEP parser, SPEM engine, or operational OSLC federation.

## Primary scientific foundations checked against the supplied files

- `SemanticCartography.html`, CAiSE 2025 masterclass, *Proposed Approach: Semantizing Interactive Compound Graphs*: T1 (textual syntax of types), T2 (visual symbols), T3 (mappings through Cytoscape selectors and styles), and T50 (create a visual notation where none exists). ArchiCG is cited as a demonstration prototype. **Scope:** principles for semantizing representations, not a complete configuration model.
- `IESA2026/Semantic Cartography — I-ESA 2026 [20 min].pdf`, slide 5: Applied Semantic Cartography (ASC) is a cognitive visualization layer based on formal semantics retained in native models; it is neither a new semantic standard nor a translation layer. Slide 6: Cytoscape.js, fCoSE, and expand-collapse for compound graphs, with types and rendering derived from specifications. Slide 7: arbitrarily nested containment and cross-boundary links. Slide 10: polyglot unification is not considered solved; STEP support was demonstrated on Part 21 instances but not yet on EXPRESS schemas. This last caveat precludes claiming a fully validated STEP schema federation.
- `MasterclassInteroperabilitéSémantique.pdf`, `SemanticInteroperability.html`: complementary materials on semantic interoperability; no STEP/SPEM conformance or implementation is attributed to them without analysis of the relevant sections.
- `hypermodel.html`: HTML prototype titled *ArchiMate ↔ BPMN Visual Mapping*; it does not, by itself, constitute a normative hypermodel definition.

The research-sources ZIP was supplied by the user on 2026-10-26. The original files remain under their authors' authority; no large training file is reproduced in this deliverable.

## Identities and relationships: minimal E3.1 contract

| Element | Identity | Invariant |
|---|---|---|
| `Definition` | `def:*` | Reusable identity independent of usage and views |
| `Occurrence` | `occ:*` | Own identity, references a definition, belongs to a composition, carries a role |
| `Composition` | `comp:*` | Architectural scope, not automatically a STEP assembly |
| `Connection` | `conn:*` | Explicit typed relationship between occurrences, with semantic provenance |
| `FederatedReference` | `ref:*` | Authority, native locator, granularity, selection, and pinning status |
| `Configuration` | `baseline:*` | Consistent selection of versions for occurrences in a composition |
| `Cytoscape projection` | Preserved IDs | `data.parent` means **visual membership in a container**, not native aggregation |

Reusing a *definition* in two configurations creates two *occurrences*, even if the selected constituent revision is identical. Connectivity links differ from decomposition; neither is inferred from Cytoscape containers.

An unpinned federated reference (`pinned:false`) cannot guarantee a reproducible baseline. E3.1 describes local selections and user references, **not yet** an immutable digest-based lockfile or synchronization with external managers. The validator flags incomplete references but does not invent native versions or creation timestamps.

## Resolution, temporality, and limitations

The two E3.1 baselines reuse the four illustrative components of the E3 resolver: `baseline:reference` is linked to `case:resolved` (declared constraints satisfied); `baseline:alternative` is linked to `case:incompatible`. The third E3 case, `case:indeterminate`, remains in `configurations.json` but is not shown by a third composition: it tests insufficient evidence independently of structure.

Dates: `observation` values indicate integration dates in the example, not intrinsic resource validity. Presentation versions are those in the supplied files; Git/ZIP metadata is not treated as normative publication dates.

**Remaining work:** complete cross-cutting registry of Atlas Markdown/concepts/relationships, selections based on actual Git revisions, qualified assertion provenance, effectiveness policies, immutable revisions, native adapters, configurable types/notation language, impact analysis, semantic-preservation tests, and experiments on real systems. The demonstrator does not yet meet these goals.

## Usage

After application, `npm test -- --run` checks the E3 core and seven E3.1 invariants; `npm run build` compiles the enriched page. The E3.1 section is inserted below the existing page to avoid modifying the validated E2 map. The menu switches between two visual configurations and lets users inspect original identifiers.
